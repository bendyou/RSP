# Лабораторная №2 · REST API CommandX

Дисциплина: «Разработка серверных приложений». Продолжение [архитектуры №1](../lab1/ARCHITECTURE.md). Результат: **22 операции на 17 путях, 31 схемы, OpenAPI 3.0.3**.

## 1. Границы и совместимость

Контракт описывает основной срез существующего Django REST Framework backend: регистрацию/JWT, собственный профиль, полный CRUD серверов, SSH-команду, проверку подключения, метрики, доступ в панели, подписки, транзакции, чтение пользователей администратором и AI. Плюс `/api/health/`, добавленный только для каркаса лабораторной №3. Остальные методы в №3 пока не реализованы.

Префикс исходного проекта `/api/` и завершающие слеши сохранены. В OpenAPI `servers.url` равен `http://127.0.0.1:8000/api`, поэтому `paths` не повторяют `/api`. Не вводятся `/api/v1`, email-login, отдельные роли operator/viewer, коллекции книг, инциденты или фоновые агенты.

Вне среза: файловые действия `ls`, `upload_file`, `create_file`, `create_directory`, `rename_file`, `read_file`, `write_file`, `delete_file`, `search_files`; `stats`, `warmup`, альтернативный PUT профиля, административные update/add-balance, toggle/delete-user, grant-subscription и служебные маршруты Django/DRF. Это реальные возможности исходника, но они не объявлены реализованными в учебном каркасе. `AllocatedServer` не имеет активного API; отдельный CRUD для него не придуман.

## 3. Аутентификация и доступ

Глобальная схема `bearerAuth` — HTTP Bearer JWT. Исключения `security: []`: регистрация, token, refresh и health. Вход по `username/password`, регистрация с `password_confirm`. Access действует 1 час, refresh 7 дней; refresh не ротируется по текущим настройкам. Запросы защищённых ресурсов передают `Authorization: Bearer <access>`.

Обычный пользователь читает и меняет только свои серверы. `created_by` задаёт backend; подмена клиента не меняет владельца. Чужой сервер скрыт ответом 404 даже от администратора. `/admin/users/` требует `is_staff`; обычный пользователь получает 403. Приостановленный сервер блокирует SSH-действия кодом 403, но допускает чтение карточки, изменение, удаление и историю метрик.

## 4. Данные и фактическое поведение

- Все обычные тела — JSON, аватар дополнительно поддерживает multipart. Секреты SSH write_only и отсутствуют в схемах ответов. В БД они ещё не зашифрованы.
- SSH-порт 1–65535; имя/SSH username — до 120, host — до 255. Для создания нужен пароль либо ключ по auth_type. При PATCH старый секрет сохраняется, если он не передан. Условие валидности реквизитов при обновлении зависит от сохранённой записи и проверяется сервером, а не одной JSON Schema.
- DRF может игнорировать неизвестные и read_only поля. Поэтому контракт не обещает строгий запрет всех лишних полей; `additionalProperties: false` не установлен искусственно.
- PUT сервера требует name/host/username, но необязательные пропущенные значения могут сохраняться в существующем serializer.update. PATCH допускает частичное и пустое обновление. Замена поведения на строгий PUT — отдельное изменение совместимости.
- История содержит не более 2000 последних сэмплов за 1–168 часов, возвращает их по времени ASC. Неизвестные метрики — null. Список серверов — PageNumberPagination по 20, транзакции и пользователи — обычные массивы.
- `exec` с ненулевым exit code возвращает HTTP 200 и success=false. Неуспешная проверка SSH также может вернуть 200. Нельзя считать HTTP 200 доказательством успеха удалённой команды.
- `toggle_status` — неидемпотентный POST, он меняет доступ в панели. Это маршрут существующего проекта, а не пример чистого resource naming; переименование сломало бы frontend.
- Текущие метрики при GET могут сохранить технический сэмпл. Это существующая особенность проекта; GET не используется для запуска пользовательских shell-команд.
- Пополнение без эквайринга выключено по умолчанию (403). Покупка списывает баланс и задаёт срок подписки от текущего времени. Десятичные суммы хранятся в БД как numeric; исходник выдаёт JSON number через float.

### Общая схема ошибок

`ErrorResponse` используется всеми описанными JSON-ошибками. Она допускает реальный DRF `{"detail":"..."}`, ошибки полей `{"port":["..."]}` и собственные `{"error":"...","success":false}`. Открытая схема сохраняет совместимость вместо выдуманного envelope code/message/timestamp. На маршрутах auth также может присутствовать code. Необработанное исключение Django способно вернуть HTML 500; полная нормализация ошибок потребует отдельного exception handler в следующих работах. OpenAPI не реализует его автоматически.

## 5. Примеры

Добавление сервера:

```http
POST /api/servers/
Authorization: Bearer <access>
Content-Type: application/json

{"name":"Учебный VPS","host":"server.example.com","username":"student","auth_type":"password","password":"Example-ssh-pass!"}
```

Результат — 201 с карточкой сервера без password/private_key/passphrase. Изменение имени без сброса реквизитов: `PATCH /api/servers/1/` с `{"name":"Новый заголовок"}`. При удалении `DELETE /api/servers/1/` возвращает 204 без JSON. Эти запросы относятся к полному исходному CommandX; учебный №3 пока отвечает только на health.

## 6. Контрольные вопросы

1. **Query, Path, Request Body.** Path идентифицирует ресурс (`/servers/{id}/`), query уточняет выборку (`metrics_history/?hours=24`), body передаёт создаваемые/изменяемые данные (`name`, SSH-реквизиты). Секреты не помещают в URL: он попадает в историю и логи.
2. **Идемпотентность.** Повтор одного запроса имеет тот же целевой эффект. GET читает ресурс, PUT задаёт его состояние, DELETE обеспечивает отсутствие ресурса; ответы на повторы могут отличаться. POST обычно создаёт ресурс или запускает действие, и повтор может иметь новый эффект. Техническое логирование/сэмпл при GET не делает его командой изменения бизнес-ресурса. Повтор SSH-команды после таймаута особенно опасен: результат первой попытки может быть неизвестен.
3. **401 и 403.** 401 — отсутствует/неверен/истёк JWT либо неверные credentials. 403 — пользователь распознан, но не имеет административной роли или доступ к серверу приостановлен. Чужие серверы намеренно дают 404, скрывая существование объекта.
4. **components/schemas и $ref.** Переиспользуют одну модель в нескольких запросах/ответах, сокращают дублирование и упрощают согласованное изменение. Например, все ошибки ссылаются на ErrorResponse, массив истории — на MetricHistoryItem.
5. **PUT и PATCH.** В REST PUT представляет замену состояния, PATCH — частичное обновление. У существующего DRF-проекта PUT требует основные поля и может сохранить пропущенные необязательные значения. Эта особенность явно описана в контракте; PATCH сохраняет всё не переданное клиентом.
