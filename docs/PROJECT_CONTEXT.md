## Отличия стадии обучения

Лабораторная №1 документирует существующую предметную область и физическую модель. Учебный SQL экспортирован из ORM в пустой PostgreSQL; служебные таблицы auth включены для внешних ключей. Это не копия рабочей БД и не новая миграция.

Лабораторная №2 описывает основной срез API исходника и дополнительный health-check. Полный файловый API, управление пакетами через shell, часть административных действий и служебный API-root находятся за пределами этого среза. В `lab2/ARCHITECTURE.md` указаны границы и особенности фактического поведения. Единая схема ошибок допускает реально используемые формы DRF и собственных views.

Лабораторная №3 содержит только настройки, слои, DRF-контроллер и health-check. Наличие эндпоинта в OpenAPI №2 не означает, что он уже реализован в №3. Функциональные маршруты должны появляться в дальнейших работах по их заданиям.

## Ограничения исходника, которые нельзя скрывать

- SSH-секреты хранятся в БД открытым текстом; `write_only` лишь исключает их из JSON. Пароль пользователя Django хранит как хеш.
- Ограничения `choices` не становятся SQL CHECK автоматически; диапазон SSH-порта 1–65535 проверяет сериализатор, в БД есть лишь `port >= 0`.
- У `ServerMetric` два nullable FK без XOR CHECK; приложение обычно пишет один, БД не гарантирует это правило.
- `email` стандартного `auth.User` не уникален в БД, хотя регистрация проверяет его на уровне приложения. `auth_user.id` остаётся INTEGER из стандартных миграций Django.
- Баланс, тип подписки и её срок — текущий снимок в профиле; это не полноценный бухгалтерский журнал.
- SSH-команды могут иметь побочные эффекты; их нельзя автоматически повторять после неоднозначного таймаута. Ключи хостов должны быть заранее проверены.
- Нет отдельного агента мониторинга, очереди задач, полноценного аудита команд и таблиц инцидентов/рекомендаций.

Улучшения этих ограничений допустимы только в пределах конкретного задания с явным описанием изменений схемы, API и совместимости.
