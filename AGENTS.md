# Инструкции для агента

Сквозной проект — **CommandX**, панель управления собственными серверами по SSH. Дисциплина: «Разработка серверных приложений».

## Организация веток

- `main` — только описание темы, навигация и эти инструкции. Не добавляй в неё отчёты, код, схемы БД или спецификации лабораторных.
- `lab1` — только файлы лабораторной №1, непосредственно в корне ветки: архитектура, диаграммы и схема БД.
- `lab2` — только файлы лабораторной №2 в корне: отчёт, OpenAPI, Swagger UI и проверки контракта.
- `lab3` — файлы этапа №3 в корне: каркас Django/DRF, конфигурация, health-check и тесты; ARCHITECTURE.md и openapi.yaml включены как контекст, указанный в методичке.
- Ветки не объединяются в накопительный каталог работ. Между работами используй ссылки на соответствующие ветки GitHub.

Новую лабораторную выполняй в отдельной ветке по её номеру. Если нужен код предыдущего этапа, возьми за основу соответствующую ветку (для будущей №4 — `lab3`), затем добавь только материалы, необходимые новой работе. В `main` обновляй лишь описание и ссылку. Не сливай ветку лабораторной в `main`.

## Основа проекта

- Python, Django 5.2, Django REST Framework, SimpleJWT; React/TypeScript/Vite во frontend. Не заменяй backend на FastAPI и не меняй тему на коллекции книг или вымышленную систему инцидентов.
- Маршруты исходника: `/api/` с завершающим `/`. Не вводи `/api/v1` и не переименовывай пути без задания и описания совместимости.
- Регистрация: username, email, password, password_confirm. Вход: username/password. Токены: access/refresh.
- Роли: пользователь и администратор (`is_staff`). Серверы фильтруются по `created_by` даже для администратора.
- Сущности: стандартный auth.User, UserProfile, Server, ServerMetric, Transaction и legacy AllocatedServer. Не добавляй таблицы ради количества.
- `Server.is_active` управляет доступом в панели, не питанием ОС. Метрики собираются по запросу через SSH. Реального эквайринга нет; AI опционален.
- №3 содержит каркас и основной `GET /api/v1/health` по методичке; также работают `/health` и прежний `/api/health/`. Это исключение для health, а не перенос функционального API на /api/v1. JWT, CRUD, модели и миграции ещё не реализованы; их операции в OpenAPI помечены x-lab3-implemented=false.
- Перед запуском №3 выполняй `python tools/init_env.py`: секрет Django обязателен и не имеет литерала по умолчанию. Сохраняй существующий непустой секрет и параметры локального .env; тесты должны использовать отдельный случайный секрет без чтения рабочего файла.

## Следующие работы

Лабораторная №4 **не выполнялась**. Не создавай её код, ветку или миграции до отдельного запроса пользователя. После такого запроса прочитай задание и продолжай каркас №3, сохраняя `controller → service → repository` и отдельную конфигурацию.

Схему развивай миграциями Django и проверяй на отдельной БД. Учебный `database/schema.sql` из ветки lab1 — снимок DDL, его нельзя применять к рабочей базе. Стандартный auth_user.id — INTEGER, собственные модели — BIGINT. SSH-секреты в исходнике ещё не зашифрованы; write_only лишь скрывает их из JSON. Не приписывай БД отсутствующие CHECK, UNIQUE или XOR-ограничения.

При изменении API обновляй отчёт и OpenAPI в ветке соответствующей работы; при изменении модели — ERD и словарь данных. Не копируй чужие лабораторные целиком ради ссылок. Контекстные документы и необходимые инструменты проверки могут находиться в каждой рабочей ветке.

## Проверки и публикация

Пользуйся командами из README текущей ветки. Проверки не должны обращаться к рабочей БД, SSH-хостам, реальным платежам или AI. Не заявляй об успехе без запуска.

Не переписывай историю и не выполняй force-push без отдельного разрешения. Не создавай GitHub-комментарии, не добавляй Co-authored-by или атрибуцию агента. Сообщения коммитов — краткие, без тела. Не добавляй комментарии в новый код.

Не публикуй .env, SSH-ключи, пароли, дампы, пользовательские данные, архивы и виртуальные окружения. Исходный pic_project используй для чтения, если отдельно не поручено его изменение.
