# Лабораторная работа № 3 — каркас серверного приложения

**Тема проекта:** «Интеллектуальная панель управления серверами» из [корневого ARCHITECTURE.md](../ARCHITECTURE.md). Цель этой лабораторной — подготовить слои приложения, конфигурацию и проверку доступности API. Сценарии управления серверами и работа с PostgreSQL здесь ещё не реализованы.

## Структура

```text
lab3/
├── app/
│   ├── config/       # .env и проверка настроек
│   ├── controller/   # HTTP-маршруты и формы ответа
│   ├── service/      # логика сценариев
│   └── repository/   # место для слоя доступа к данным
├── main.py           # сборка приложения и точка входа
├── .env.example      # безопасный шаблон настроек
├── requirements.txt
└── README.md
```

`controller` вызывает `service`; сервис не зависит от HTTP. Для health-check репозиторий и база данных не нужны: маршрут проверяет работающий процесс API. Зависимости соединяются в `create_app()`, что позволяет подменять настройки при проверке.

## Запуск

Из каталога `lab3`:

```sh
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
python main.py
```

При необходимости измените `HTTP_HOST` и `HTTP_PORT` в `.env`. Переменные, заданные в окружении процесса, имеют приоритет. `.env` исключён из Git корневым `.gitignore`; в нём не следует хранить рабочие секреты вместе с исходным кодом. Шаблон содержит только несекретные значения.

Проверка:

```sh
curl -i http://127.0.0.1:8080/api/v1/health
```

Ожидается `200 OK`, `Content-Type: application/json` и ответ вида:

```json
{
  "status": "pass",
  "app_name": "Интеллектуальная панель управления серверами",
  "version": "1.0.0",
  "environment": "development",
  "uptime_seconds": 0
}
```

`uptime_seconds` — целое число секунд с создания экземпляра приложения, поэтому фактическое значение изменяется. Маршрут также доступен в Swagger UI: `http://127.0.0.1:8080/docs`.

## Связь с предыдущими лабораторными

Корневой архитектурный документ описывает панель серверов. Материалы в `lab1` и `lab2` описывают отдельный вариант «Моя библиотека»; они не менялись и не подключались к данному каркасу. Спецификация `openapi.yaml` в корне относится к библиотеке, поэтому не объявляется контрактом реализованного здесь API. Единственный реализованный маршрут — `/api/v1/health`.

## Краткие ответы на контрольные вопросы

1. Сервисный слой не должен знать структуру HTTP-запроса, чтобы один и тот же сценарий можно было использовать из HTTP, фонового обработчика или CLI и проверять отдельно.
2. Секреты в коде попадают в историю Git, становятся доступны всем получателям репозитория и требуют ротации после утечки.
3. `.env.example` документирует обязательные настройки без публикации локальных значений и помогает воспроизвести запуск.
4. Health-check позволяет оркестратору или оператору проверить, что процесс API отвечает. Текущий маршрут проверяет только API, а не PostgreSQL или агенты.
5. Инверсия зависимостей позволяет сервису работать с интерфейсом репозитория, а конкретную реализацию БД передавать при сборке приложения. Поэтому бизнес-логика не зависит от драйвера PostgreSQL.
